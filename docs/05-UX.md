# 5. UX rules every Lin* app keeps

Distilled from the LinPrinter GUI Guide and Design Reference (2026-10-02), which applies the ten
UX laws, the ten 2026 design principles and WCAG 2.2 AA. These are the rules the components
enforce or make easy.

## 5.1 Structure

- **Four destinations at most** in the rail: the job (Print, Scan, Copy…), Activity, the device,
  Settings (About lives in Settings and the header menu).
- **One main action per view**, the `big` primary button, bottom right, never scrolled away.
- **Progressive disclosure**: everyday choices visible, at most four option groups, the rest
  behind "More options".
- **The result next to the choices**: a live preview beside the options, not on another page.

## 5.2 Status and messages

- Four states, one vocabulary everywhere: **Ready · Busy · Needs you · Can't reach**, each an icon
  and a word (`lintheme.status`).
- Every message: **what happened · why (with evidence) · the next step** (`status.message`).
- Lead with the cheapest physical check. For USB devices: another cable first
  (`status.CABLE_FIRST`). In 2026 two faulty cables caused a week of LinPrinter failures while the
  printer, the computer and the software were blamed in turn.
- Honest uncertainty: show the measurement ("27 of 200 requests failed"), name what isn't known.
- Technical detail goes behind Details, never in the headline (`status.problems` checks).

## 5.3 Control and safety

- **No silent automation.** Never switch route, reconnect or retry mid-job without telling the
  user; recovery is a button that states its scope. (LinPrinter's silent fallback spooled a job
  onto a failing link and hung the printer.)
- **Confirm only destructive actions**, with a title that asks and buttons that are verbs
  (`confirm(..., destructive=True)`). Undo where possible instead.
- **Disabled controls say why**, beside them (`disabled_with_reason`).
- **No dark patterns**: no fake urgency, no pre-ticked extras, no nagging; Cancel as easy as Start.
- **No AI, no network, no telemetry**, and the Settings page says so.

## 5.4 Accessibility (WCAG 2.2 AA)

| Criterion | How the kit meets it |
|---|---|
| 1.4.1 Use of colour | status = icon + word; gauges print the percentage and "Low" |
| 1.4.3 / 1.4.11 Contrast | tokens tested: text ≥ 4.5, outlines and focus ≥ 3 |
| 2.1.1 Keyboard | real buttons, radio groups, Alt+1…9 for pages, Ctrl+P / Ctrl+O conventions |
| 2.4.7 Focus visible | 2 px focus ring, 2 px offset, `#ffd75e` |
| 2.5.8 Target size | ≥ 32 px everywhere (floor 24); main action 48 |
| 3.3.1 / 3.3.3 Errors | `set_invalid` + the fix in words |
| 4.1.2 Name, role, value | accessible names on every control; tests assert them |
| 4.1.3 Status messages | chip and banners carry accessible names that change with state |

Test with a keyboard only and with Orca before calling a page done.
